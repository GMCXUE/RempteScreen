# Windows 接收通话声音刺耳：播放链路修复

用户确认问题是 Windows 听手机或 Mac 的语音/视频通话声音时刺耳。本次聚焦接收播放，不将尚未验证的麦克风回声、WASAPI 屏幕音频采集问题当作根因。

## 已确认的代码问题与修改

- 原缓冲逐个 i16 采样入队；满队列时等待后丢掉单个采样，可能使立体声左右声道错位。改为一个槽保存完整的左右声道帧，入队前检查整个 PCM 包容量，不足时丢整个包，消除部分入队和逐采样等待。
- 原播放启动/断流后直接以空队列输出零值，没有启动预缓冲和淡出。增加 30ms 预缓冲、5ms 淡入淡出，断流后重新缓冲，降低短时抖动造成的爆音。
- 原来将默认输出设备的声道数直接传给 WebRTC。对 5.1/7.1 Windows 输出端点，改为请求单声道/立体声 PCM，再映射到物理前置 L/R；其他物理声道输出静音。采样率仍由 SDK 转换到设备默认采样率，不擅自改变设备速率。
- 支持 CPAL 的有符号、无符号整数及浮点输出格式。无符号静音使用中点；将音量上限限制到 100%，平滑调整，避免软件增益意外放大或削波。
- 持续接收音频时也检查停止标志，避免停止定时器被连续音频饿死。
- 输出日志包含设备、速率、物理/解码声道和格式。每 10 秒及退出时记录欠载、整包溢出、异常帧及接收 PCM 近满幅比例，帮助区分播放问题和上游声音已经失真的情况。仅记录统计量，不保存通话内容。

## 双端一致性与平台差异

本次不增加业务功能、协议、界面入口或改变手机的发送参数。桌面 Mac/Windows 共用上述播放缓冲；Flutter 使用原生 WebRTC 的 AudioTrack 播放及其抖动缓冲，不经过 Rust 的 CPAL/rtrb 路径，因此不复制桌面自管播放实现。移动端的语音和视频通话仍使用相同的麦克风轨与音量/扬声器交互。系统声音采集与通话麦克风仍独立。
