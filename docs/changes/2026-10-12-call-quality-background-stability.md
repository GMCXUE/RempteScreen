# 视频通话画质、帧率与 Android 后台稳定性

电脑与手机互通时，原先手机只请求 640×360 / 24 fps，且未覆盖 SDK 编码档位（该分辨率默认约 450 kbps / 20 fps）；桌面摄像头发布限制为 900 kbps / 24 fps。桌面接收帧还经过 40 ms 到达间隔过滤，30 fps 输入会被减半，24 fps 的到达抖动也会造成额外丢帧。

本次在 Rust 主桌面和 Flutter 客户端统一摄像头目标：1280×720 / 30 fps、H.264、2 Mbps 编码上限、单层发布，带宽不足时优先保帧率。Android 摄像头实际分辨率仍由设备协商，macOS 摄像头不支持 720p 时保留 VGA 回退；只有设备支持 30 fps 时才固定 macOS 采集时长。屏幕共享继续使用用户选定的独立编码参数。

桌面摄像头帧处理移除 40 ms 过滤，使用 SDK 已有的单帧有界队列；RGB 转换和 JPEG 编码放到阻塞工作线程，摄像头显示 JPEG 质量提高至 85。完整通话、悬浮窗和观看窗口的刷新不再限制在 10–20 fps，并对此前缺少超时的摄像头帧请求增加超时重试。摄像头处理每 10 秒记录尺寸和处理帧率，供后续实机诊断。

Android 系统记录在 2026-10-11 17:23 和 2026-10-12 21:34 出现相同的 WebRTC 信令线程 SIGABRT。用匹配 Build ID `8939406b3b9fa259` 的本地库核对，崩溃路径为 `onAddTrack` 的 Java 异常经 JNI 升级为进程终止；原始 Java 异常详情已不在环形日志中，因此不能宣称已确定该次崩溃的具体 Java 行。

代码中的明确风险是：悬浮窗查找轨道时回退到 `getTransceivers()`，同时信令回调也刷新该列表。已解析的 SDK 字节码显示，这个方法会 dispose 上次返回的对象。本次取消悬浮窗、SDK 渲染器及新 UUID 查询的此回退，通过回调维护远端轨注册表；回调期间先保存元数据快照，随后在主线程依次更新注册表、查询 transceiver 并发送事件。关闭后的迟到回调不再访问 peer；快照和平台处理错误记录完整异常，不逃逸至 JNI。延迟的渲染器绑定会检查当前轨身份，失效的轨不会再次绑定。

移除回调可能提供同一接收器的新 Java 包装对象，因此注册表额外记录 receiver ID，按接收器归属清理；旧接收器或旧流的迟到移除不能删除替换轨。这里的 Android 改动是原生对象生命周期修复，不增加后台重新获取摄像头权限的路径。

上游对象寿命参考：[WebRTC peer connection 回调](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/src/jni/pc/peer_connection.cc)、[JavaMediaStream 的释放](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/src/jni/pc/media_stream.cc)。本次依赖版本与崩溃地址的判定以本地实际 AAR 和库 Build ID 为依据。
