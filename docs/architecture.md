# 架构与选型决策

## 一、整体链路

系统分成两个平面，职责不重叠：

```
        ┌──────────────────────────────────┐
        │  设备目录服务（控制面）             │
        │  · 设备 ID 分配与在线状态           │
        │  · 连接密码校验与刷新               │
        │  · 签发带权限的访问令牌             │
        └──────────────────────────────────┘
             ▲                       ▲
  ①注册与心跳 │                       │ ④提交「设备 ID + 密码」
             │                       │
    ┌────────┴────────┐     ┌────────┴────────┐
    │  采集端 App      │     │  接收端 App      │
    │  macOS / Windows │     │  iOS / Android  │
    │  画面 + 系统音频  │     │  画面 + 声音     │
    └────────┬─────────┘     └────────▲────────┘
             │ ②推流                  │ ⑤拉流
             ▼                        │
        ┌──────────────────────────────────┐
        │  自托管 LiveKit（媒体面）          │
        │  SFU + TURN   7880/7881/7882     │
        └──────────────────────────────────┘
```

**控制面**只管「谁是谁、能不能连」，完全不碰音视频；**媒体面**只管转发，不关心设备身份。两者只通过一枚令牌耦合：目录服务签发，LiveKit 校验。

采集端只推一路流，接收端数量增长不影响采集端上行带宽——这是选择 SFU 而非 P2P 的核心原因。

## 二、决策记录

### 决策 1：采集端与接收端都做原生 App

用户明确要求双端 App。这个选择带来一个必须正视的后果：接收端原本可以做到零安装（手机浏览器直接播放），改为原生后需要双端开发、签名与上架，用户也要多一步安装。

**收益**是换取完整可控性：后台常驻、音频路由、码率与画质策略、断线重连时机都由自己掌握，不再受浏览器行为约束。

### 决策 2：媒体层用自托管 LiveKit，不自研信令 + P2P

| 方案 | 取舍 |
| --- | --- |
| 自研信令 + 纯 P2P | 仅在 1 对 1 时可用。采集端上行要乘以观众数，多一台设备看就多一份上行，家用宽带上行通常只有 20–50 Mbps，两台平板同时看就可能卡顿 |
| 自研 SFU | 等于从零写一个实时媒体服务器，工作量以月计，且要自己解决 TURN、拥塞控制、丢包重传 |
| **自托管 LiveKit（选定）** | 单二进制服务，SFU 与 TURN 一体；官方提供 Swift（iOS / macOS）、Kotlin（Android）、Web 三套 SDK，客户端开发量大幅下降 |

选它主要是为了客户端 SDK：本项目要写四个客户端，能直接复用成熟 SDK 比自研信令协议节省的量级更大。

### 决策 3：macOS 采集端必须原生，Windows 端优先 Electron

关键差异在系统音频：

- **macOS**：Chromium 的 `getDisplayMedia` 拿不到系统音频，只能采到麦克风。方案要么让用户额外安装虚拟声卡（BlackHole / Loopback），要么用原生 `ScreenCaptureKit`——后者在 macOS 13+ 可直接 `capturesAudio = true` 采到系统声音，是干净的正解。
- **Windows**：Chromium 支持 WASAPI loopback，`getDisplayMedia({ audio: true })` 在 Windows 上可以拿到系统声音。所以 Windows 端可以先用 Electron 快速落地，不必一上来就写 C++。

因此两端技术栈不同是**有意为之**，不是不一致。

### 决策 4：先做显示器级采集，窗口级与区域级后置

`SCContentFilter` 支持三种范围：整屏、单个窗口、自定义区域。第一版只做整屏与单窗口，区域选择涉及交互式框选 UI，成本高且非核心。

## 三、配对协议

连接模型对齐 ToDesk：**无账号体系，凭「设备 ID + 连接密码」配对**。完整接口契约见 [`server/README.md`](../server/README.md)。

### 设备 ID

- 9 位数字、首位非零，由服务端分配
- 只保证在**当前在线设备之间**不重复，不做永久绑定
- 采集端持久化到本地，重启时带上即可沿用原 ID
- 用 9 位纯数字是为了电话报读和口头转述时不容易出错

### 连接密码

- 6 位，字符集 `23456789abcdefghjkmnpqrstuvwxyz`，剔除 `0 O o`、`1 l I`
- 每次注册与每次刷新都重新生成，**不跨会话复用**
- 服务端只存 scrypt 派生值，不存明文
- 同一设备 60 秒内错 5 次即冷却 60 秒

### 房间与身份

设备 ID 直接决定房间，不再额外发明房间码：

```
房间名 = device-<设备 ID>        例如 device-601661063
```

| 身份 | 令牌权限 | 说明 |
| --- | --- | --- |
| `caster` | `canPublish=true`、`canPublishData=true` | 采集端，发布屏幕、系统声音及可选通话轨 |
| `viewer` | `canPublish=true`、仅 `CAMERA/MICROPHONE`、`canPublishData=true` | 接收屏幕，同时可发布通话轨和发送文件 |

权限写死在签发的 JWT 里。观看端只能发布摄像头与麦克风，不能发布或替换屏幕共享轨；可靠数据通道只承载文件传输协议。

### 轨道约定

- 画面轨：`trackName = "screen"`，采集屏幕内容
- 音频轨：`trackName = "system-audio"`，采集系统声音
- 摄像头轨：`source = CAMERA`，显示在独立小窗
- 麦克风轨：`source = MICROPHONE`，用于双向语音

接收端按 LiveKit `source` 区分屏幕、系统声音、摄像头和麦克风，通话开关不会影响屏幕共享。

### 为后续的可控能力预留

若之后要加远程控制，**不需要动媒体面**：LiveKit 数据通道已经用于文件传输，但客户端目前只处理
`rs-file-ctl` 与 `rs-file-bin` 主题。远程控制仍需单独设计输入事件协议与授权开关。

### 独立文件房间

文件页面使用 `files-{deviceId}` 数据房间，设备注册时取得 fileToken 并上线接收。观看继续使用 `device-{deviceId}` 媒体房间，两者分别持有连接与生命周期。`purpose` 在密码连接和确认请求中一致传递，界面名称不参与协议决策。发送方验证目标参与者的 ready/saved 回执后推进状态，详见 [双端修整说明](changes/2026-10-10-session-reliability.md)。


### 消息与来电后台接收

当前 primary Rust 桌面与 Flutter Android 使用原生后台同步，只覆盖应用/消息服务仍可运行的普通后台接收。用户确认暂不接入进程被清理后的厂商推送；保留现有 NativeMessaging 封装、通知动作路由和服务端事件标识作为后续接入点，详见 [通知接收范围与接入契约](design/notification-delivery.md)。
