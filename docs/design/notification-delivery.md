# 通知接收范围与后续接入点

2026-10-11 用户确认：当前只实现普通后台接收；进程被清理后的系统推送留待后续，不申请厂商账号，不集成厂商 SDK、FCM 或 APNs。

## 当前双端行为

通知体验、开关、限频、已读和平台差异的最新规则见 [通知策略检查与优化](../changes/2026-10-14-notification-policy-review.md)。

- Rust 桌面客户端：应用仍运行时，由原生线程同步消息和通话，不依赖消息页是否显示。消息交给系统通知；Mac 来电使用持续浮层。
- Flutter Android：登录后由 MessagingService 的 remoteMessaging 前台服务同步消息和通话，不依赖 Dart 后台定时器。切到其他应用、划掉界面任务时不主动停止消息服务。系统是否保留服务仍取决于用户的后台、电池与通知设置。
- 消息通知、好友申请、语音和视频来电共用账号校验、前台会话抑制和通知点击流程。通话操作仍由现有通话控制器执行。
- 退出登录停止接收并清理通知；通知点击必须核对当前账号、好友和通话状态。没有后台自动启动摄像头或麦克风的路径。
- 当前不承诺在进程被清理、设置中强行停止、断网或系统冻结期间实时送达。重新打开应用后恢复同步。

当前实现与检查状态见 [后台通知修整记录](../changes/2026-10-11-background-notification-fix.md)。代码检查已通过，新版本尚未覆盖安装，普通后台通知的实际展示仍待实机确认。

## 已有接入点

保留现有封装作为未来推送入口，暂不增加空实现或未启用的服务端 API：

| 层 | 现有入口 | 后续用途 |
| --- | --- | --- |
| Flutter | `NativeMessaging` | 继续统一账号启动/停止、设置、通知点击与来电清理；未来 SDK 适配留在原生层 |
| Android | `MessagingService.postNotice`、`openIntent` | 共用通知构建和点击路由，推送接收器复用提醒策略 |
| Rust 桌面 | `notifications.rs`、`messaging-action` | 共用账号校验、点击路由和通话浮层 |
| 服务端 | social state 的 `lastIncomingSeq`、好友申请 ID、call-state 的 call ID | 作为后续投递事件与去重依据，现有接口保持可作为重同步来源 |

## 后续接入契约（尚未实现）

未来推送适配器只增加“事件到达”的来源，聊天、通话界面与媒体流程继续共用：

- 基础路由沿用 `kind=message/friends/call`、`accountId`、`peerId`；来电沿用 `callId`。
- 消息增加对应的消息序号/事件标识，按账号和事件去重；厂商推送与轮询同时启用时，同一事件只提醒一次。
- 推送仅是提醒和重新同步的线索，不携带登录令牌、LiveKit token 或通话接通授权。点击后使用当前登录会话确认服务器状态；过期来电不能直接启动媒体。
- 厂商设备注册信息与当前账号绑定，账号切换和退出时解除旧绑定。服务端适配器独立于消息写入与通话状态事务。
- 厂商密钥只由服务端配置管理；没有有效配置时仍使用普通后台接收，不显示“已启用系统推送”。

接入厂商推送前再确定平台、开发者账号、应用审核与设备注册 API，本阶段不实现上述推送部分。
